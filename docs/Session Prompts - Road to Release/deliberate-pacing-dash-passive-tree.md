## Design Decisions (locked, baked into every prompt below)

- **Slowdown method:** rebalance individual speeds via data — *not* `Engine.time_scale`. Animations stay crisp.
- **Intensity:** ~40–50% slower overall (player base ≈ ×0.55 of current).
- **Routes to regain speed:** (1) level-up move-speed upgrades, (2) a **dash** on Spacebar with cooldown + level-up dash mods, (3) a **passive skill tree** the player spends points into (point-allocation, not hub purchases). World pickups and weapon-mod routes are *out of scope*.
- **Per-character base speed:** retune the existing 7 values against the new baseline, preserving the archetype spread (Shade fastest → Warden slowest).

GOAL: Slow the moment-to-moment game down ~40–50% so combat feels deliberate and positioning

2. ENEMY move speeds — find enemy definitions/factories (scripts/entities/enemy.gd and the enemy
   data factories under data/; check EnemyRegistry/EnemyDefinition for a move-speed field).
3. PROJECTILE speeds — both player projectiles and enemy projectiles (scripts/systems/projectile_manager.gd
   and WeaponData / enemy skill data). Slow projectiles so they can be read and dodged.
4. SPAWN density / cadence — EnemySpawnManager wave composition + spawn interval. Stretch intervals
   so the screen fills more slowly.
5. FIRE RATE / attack_speed — leave roughly as-is OR slow slightly; do NOT speed it up. (Slower
   movement already increases time-on-target.)

PER-CHARACTER RETUNE: rescale the 7 base_move_speed values in data/characters.gd by ~×0.55,
rounded to clean numbers, PRESERVING the ordering and relative spread. Starting table (finalize
with your own judgment, keep Shade fastest, Warden slowest):
   Warden 96→58 · Drifter 120→66 · Herald 120→66 · Spark 126→70 · Cursed 126→70 · Scavenger 132→72 · Shade 144→80
Note: The Cursed passive grants +20% to all base stats — make sure its post-multiplier value still
feels expert-tier, not sluggish.

CONSTRAINTS:
- Typed GDScript only (var x: float = ...). Never use := on untyped array element access.
- Expose the key multipliers/values as NAMED CONSTANTS or clearly-commented data so Ben can iterate
  fast. Do not scatter magic numbers.
- Don't break existing mod/status math (e.g. overdrive/adrenaline_rush move-speed buffs, the
  "velocity"/"assassin"/"overdrive"/"fortress" evolutions in scripts/managers/upgrade_manager.gd
  that apply ±% move_speed). Percentages stay percentages; only the bases move.
- Verify arena bounds still make sense (±800 x ±600) — slower enemies shouldn't make waves trivially
  kiteable; tune spawn density to compensate.

DELIVERABLE:
- The code/data edits above.
- A short markdown note at docs/pacing_rebalance.md recording: old vs new numbers per system, the
  multipliers chosen, and the rationale. This is the shared reference Tasks 2.1, 3.1, and 4.1 will read.

VERIFY: This is feel-critical and only observable when rendered. After editing, do NOT claim it
"feels right" — instead summarize the numeric changes and ask Ben to open Godot and playtest, calling
out specifically what to watch (player kite speed, enemy closing speed, projectile readability,
screen-fill rate). Ben prefers to run Godot himself for rendered verification.

## Task 2.1 — Spacebar dash (snappy, cooldown, charges, i-frames)
**Tier:** 3 → Opus-class
**Depends on:** 1.1 (dash distance/cooldown are tuned to the new, slower pace)
**Estimated tokens:** ~1.4k in / ~6k out

```
You are working in a Godot 4.6.1 GDScript top-down survivor game (Extraction Survivors,
E:\Projects\extraction-survivors). Read CLAUDE.md first. The global pace was just slowed ~45%
(see docs/pacing_rebalance.md) — the dash is the player's primary tool to reclaim mobility, so it
must feel FLUID and SNAPPY but be balanced by a cooldown.

GOAL: Add a dash on the Spacebar.

INPUT: Add a new input action "dash" to project.godot's input map bound to the Spacebar (Key 32 /
KEY_SPACE) and, if controller bindings exist for movement, a face/shoulder button. The existing
movement actions move_up/move_down/move_left/move_right are defined in project.godot around line 46 —
follow their exact InputEventKey format. (project.godot is plain config text; editing it directly is
fine — this is NOT a .tscn, so the no-hand-edit-tscn rule does not apply.)

MECHANIC (scripts/entities/player.gd):
- The player moves in _physics_process (~line 434) using velocity = velocity.move_toward(input_dir *
  move_speed, 1500.0*delta), plus a separate knockback_velocity term and move_and_slide().
- Implement dash as a short, high-speed IMPULSE in the current movement direction (fall back to last
  facing / aim if no input is held). "Snappy" = high speed, short duration, ease-out — e.g. dash_speed
  ≈ 520 px/s for dash_duration ≈ 0.16s (≈ 80px), tuned against the new base speeds. Expose all of these
  as named constants.
- Grant brief I-FRAMES during the dash (reuse the existing _iframes_timer / IFRAME_DURATION mechanism,
  or an is_invulnerable window — match how take_damage / _iframes_timer already gate hits at line ~522).
  Per CLAUDE.md, forces and damage must respect i-frames; the dash window should make the player
  untargetable-to-damage for its duration.
- CHARGES + COOLDOWN: support N charges (default 1) that refill on a per-charge cooldown (default
  ≈ 1.6s). A dash consumes one charge; dashing is blocked at 0 charges. Cooldown ticks in _physics_process.
- Respect crowd-control: do not allow dashing while status_effect_component.is_disabled() or
  is_movement_disabled() (same guards the movement block already uses).
- Cancel/blend cleanly with normal movement when the dash ends (don't leave residual velocity that
  feels floaty).

MODIFIER-DRIVEN STATS (critical — Task 3.1 and the passive tree depend on this):
- Do NOT hardcode dash distance/charges/cooldown as plain vars only. Add them to the player's stat
  system so upgrades can scale them. Add base entries to _base_stats and read them via get_stat():
  "dash_distance" (or dash_speed), "dash_cooldown", "dash_charges". get_stat() already resolves
  add/bonus modifiers through ModifierComponent — route dash stats the same way so a +1 charge or
  -20% cooldown upgrade is just a ModifierDefinition. Clamp dash_charges to int and >=1.

FEEL/VFX: add a lightweight dash cue — afterimage trail or dust puff and a small camera/FX nudge —
consistent with existing player VFX (see scripts/systems/player_vfx_helper.gd). Keep it cheap; this is
a survivor with hundreds of entities. No new pooled systems unless trivial.

CONSTRAINTS:
- Typed GDScript; never := on untyped array access.
- Reset dash state in player.gd::reset_stats() (run restart) — charges full, timers cleared.
- Don't regress the existing iframe/knockback/hit-flash logic.

DELIVERABLE: the input-map entry, the dash implementation, the new dash stats in _base_stats, VFX cue,
reset handling. Update docs/pacing_rebalance.md (or a new docs/dash.md) with the dash constants and the
stat keys you exposed, so Task 3.1 knows the exact names.

VERIFY: dash feel is only observable rendered. Summarize the constants and the new stat keys, then ask
Ben to open Godot and test: snappiness, i-frame timing vs enemy contact, charge refill cadence, and that
dashing is blocked under CC. Ben runs Godot himself.
```

## Task 3.1 — Level-up move-speed upgrades + dash mods

    "stat": "move_speed", "type": "percent", "value": 0.15}

ADD to upgrade_pool:
1. A second/stronger move-speed route beyond the existing "move_speed_up" (e.g. a flat "Fleetfoot"

2. Dash mods, each as an upgrade entry routed through apply_stat_upgrade:
   - "Dash Distance" — +% or +flat to dash_distance/dash_speed.
   - "Extra Dash Charge" — +1 dash_charges (type flat). Confirm player clamps charges to int.
   - "Quick Recovery" — -% dash_cooldown (a negative-percent or a dedicated reduction; match how
     apply_stat_upgrade handles the operation so the sign is correct — verify it actually REDUCES
     cooldown, not increases it).
3. (Optional, if it fits the existing EVOLUTION_RECIPES pattern) one mobility evolution combining a
   move-speed route + a dash mod (e.g. "Phase Runner": +charge and dash leaves a damaging/iframe wake),
   following the existing recipe structure with "requires"/"effects".

CONSTRAINTS:
- Typed GDScript; never := on untyped array access.
- If apply_stat_upgrade in player.gd doesn't yet handle a dash stat correctly (e.g. cooldown reduction
  semantics, or refreshing live dash charge cap), make the minimal player.gd change needed and note it.
- Keep descriptions short — they render in the level-up screen at 3× viewport scaling; don't overflow.
  After adding entries, sanity-check scripts/ui/level_up_screen.gd for row overflow.
- Don't duplicate existing entries (there is already a "move_speed_up" and move-speed evolutions
  velocity/assassin/overdrive/fortress — integrate, don't collide).

DELIVERABLE: the new upgrade_pool entries (+ any minimal player.gd wiring), verified against the
level-up UI for overflow. Summarize what you added and ask Ben to playtest in Godot if rendered
verification is wanted.

## Task 4.1 — Passive skill tree: data model, points & persistence

```
You are working in a Godot 4.6.1 GDScript survivor/extraction game (Extraction Survivors,
E:\Projects\extraction-survivors). Read CLAUDE.md and docs/hub_reference.md first. The game was
slowed ~45% (docs/pacing_rebalance.md) and a dash with modifier-driven stats was added.

GOAL: Build the BACKEND for a permanent passive skill tree the player invests points into. Points are
EARNED from leveling (point-allocation meta-progression — NOT a currency purchase). This task is data +
progression + apply-at-run-start ONLY; the hub UI is Task 4.2.

EXISTING PATTERNS TO REUSE:
- Meta-progression lives in scripts/managers/progression_manager.gd (autoload ProgressionManager). It
  already has save_data()/load_data() writing to a save file, an Array "hub_upgrades", and helpers like
  has_upgrade()/get_upgrade_tier()/purchase_upgrade(). Follow this serialization style exactly.
- Player stats route through ModifierComponent: player.gd builds base stats and adds ModifierDefinitions
  (see _apply_passive_mods and CharacterFactory.build_* ). Passive-tree effects must be expressed as
  ModifierDefinitions applied to the player's modifier_component at run start, alongside the character
  passive — NOT as bespoke per-node code.

DELIVERABLES:
1. PASSIVE TREE DATA — a new static data file (e.g. data/passive_tree.gd, class_name PassiveTreeData)
   defining nodes. Each node: id, display name, description, point cost (default 1), prerequisite node
   ids (gating), max ranks (allow multi-rank nodes), and an effect expressed as a stat target +
   operation + value compatible with ModifierDefinition (target_tag, operation "add"/"bonus", value).
   Author a STARTER TREE (~12–18 nodes) across a few branches, e.g.:
   - Mobility: +move_speed, +dash_charges, -dash_cooldown, +dash_distance (use the exact stat keys
     Task 2.1 exposed — read docs/dash.md).
   - Offense: +damage %, +crit, +projectile_size.
   - Survival: +max_hp, +armor, +pickup_radius.
   Keep values modest relative to the new baseline; reference docs/pacing_rebalance.md for move numbers.
2. POINTS ECONOMY in ProgressionManager:
   - A persisted passive_points balance + a persisted allocation map {node_id: ranks_bought}.
   - Award points from leveling. Decide and document the rule (recommended: 1 passive point per
     character level gained during a run, banked to the meta account on extraction/death). Wire the
     award where runs end / levels are recorded (record_extraction / record_death / wherever level is
     finalized — search the working copy).
   - API: get_passive_points(), can_allocate(node_id) (checks points + prereqs + max rank),
     allocate(node_id) (spends, records), refund/respec (refund_all() returning all spent points — cheap
     respec is fine for now). Include these in save_data()/load_data() with a save-version bump or a
     defensive default so existing saves don't break (load_data already does light migration — match it).
3. APPLY AT RUN START — when a run begins and the player is built, translate the allocation map into
   ModifierDefinitions and add them to the player's modifier_component (find where the player/character
   is initialized for a run; apply after character base + passive so percentages stack correctly).
   Make sure dash-stat nodes actually move the dash because dash stats are modifier-driven.

CONSTRAINTS:
- Typed GDScript; never := on untyped array access. Resource subclasses are @export data only — logic
  lives in managers/components.
- Defensive against missing keys in loaded save dicts (CLAUDE.md rule). Don't crash old saves.
- No UI in this task. Expose a clean API surface Task 4.2 can drive.

DELIVERABLE: the data file, ProgressionManager changes (points + allocation + save/load + award hook),
and the run-start application. Add docs/passive_tree.md documenting the node list, the points rule, and
the public API (method names + signatures) so Task 4.2 can build the panel against it.
