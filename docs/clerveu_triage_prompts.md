### Task 1.1: Walkability Grid + Flow Field Core System
**Tier**: 3 → Opus/Fable
**Depends on**: none
**Estimated tokens**: ~2,500 in / ~6,000 out

<role>
You are implementing a performance-critical pathfinding subsystem for a Godot 4.6 GDScript survivors-like (top-down 2D, hordes of 100–200 enemies). Read docs/engine_reference.md before writing code.
</role>

<objective>
Build a shared flow-field pathfinding system so enemies can navigate around terrain instead of grinding against cliffs. Playtest feedback confirmed enemies steer straight at the player with no obstacle avoidance and pile up on walls. Deliver a new subsystem (owned by CombatOrchestrator, child of MainArena) exposing a walkability grid and a flow field flood-filled from the player's position.
</objective>

<context>
- Terrain sources: (a) descent blocks are LDtk .ldtkl files with an IntGrid collision layer on a fixed tile grid — see docs/ldtk_schema.md for values and the descent loader for how blocks are placed in world space; (b) the base arena (±800 x ±600 px) has sparse static wall colliders on collision layer 3.
- SpatialGrid already rebuilds every frame (see tick order in CLAUDE.md) — mirror its integration style, but the flow field does NOT need per-frame rebuilds.
- All enemies share one target (the player), which is why a single flood fill beats per-enemy NavigationAgent2D at horde scale.
- Enemy movement currently lives in scripts/entities/enemy.gd (~lines 369–384); do NOT modify it in this task — Task 1.2 does the steering integration against your API.
</context>

<constraints>
- Godot 4.6, Compatibility renderer, typed GDScript throughout.
- Rebuild the flow field only when the player crosses into a new grid cell (plus a max-staleness timer, ~0.3 s); a full rebuild must stay well under 2 ms on a mid-range PC for the largest loaded descent area.
- Static walkability (from tiles/colliders) is computed once per arena/block load, not per rebuild; only the flood fill re-runs.
- Open-arena behavior must degrade gracefully: where everything is walkable, flow directions must equal the straight-to-player direction (no regression in the base arena feel).
- No allocations in the per-rebuild hot path — preallocate arrays, reuse buffers (match the pooled-parallel-array style of ProjectileManager).
</constraints>

<reasoning_guidance>
- Choose cell size deliberately (likely the LDtk tile size); document the choice.
- Use BFS (uniform cost) unless you find weighted cells; store per-cell integer distance + packed direction.
- Decide how unwalkable and unreachable cells answer get_flow_direction (suggest: nearest-walkable fallback for enemies knocked into walls).
- Think through world↔grid transforms when descent blocks are offset in world space — off-by-one here is the classic bug.
</reasoning_guidance>

<output_format>
- New script scripts/systems/flow_field.gd (or matching existing systems naming), registered with CombatOrchestrator.
- Public API: is_walkable(world_pos) -> bool, is_reachable(world_pos) -> bool, get_flow_direction(world_pos) -> Vector2, get_distance_cells(world_pos) -> int.
- A debug overlay draw mode gated behind GameManager.debug_mode (arrows or distance shading) for in-editor verification.
- Summary of design decisions + how to verify in the Godot editor. Do not claim it works until verified in-engine; prompt Ben to open Godot for verification.
</output_format>

<success_criteria>
Flow field visibly routes around cliffs in the debug overlay in a loaded descent block; rebuild cost measured and reported; open-arena directions match straight-line; API ready for Tasks 1.2 and 1.3 without changes.
</success_criteria>

**Tier**: 2 → Sonnet

</goal>

- Circle fallback: retry with jittered angles/radii (~12 attempts); final fallback = nearest walkable cell to the last candidate, so spawning never hard-fails.
- When the flow field system is absent (base arena before it initializes), behave exactly as today.
- No per-spawn allocations beyond what exists now.
- Verify in-editor: spawn a wave in a cliff-heavy descent block, confirm zero enemies appear in unwalkable/unreachable cells (debug overlay from 1.1 helps). Prompt Ben to open Godot.

### Task 3.1: Rhythm-Informed Combo Feedback — Design Brief
**Tier**: 3 → Opus/Fable
**Depends on**: Phase 1 verified in play (clean movement is the baseline for judging combat feel)
**Estimated tokens**: ~2,500 in / ~5,000 out

<role>
You are a game-feel designer working on a Godot 4 survivors-like whose validated core identity is its combo-chain combat ("street fighter in a survivors-like" — first playtest). Output is a design brief for Ben (solo dev, creative director) to redline — not code.
</role>

<objective>
Propose how to borrow rhythm-game principles — timing windows, cadence feedback, audiovisual reinforcement of "on-beat" play — to make combos feel exceptional, WITHOUT building an actual rhythm system. The playtester's exact framing: "borrow heavily from rhythm game principals" but "don't go all in… it'd overcomplicate shit way too much." Success = a small menu of concrete, cheap-to-build mechanisms with one recommended package.
</objective>

<context>
- Combo system: all 10 roster kits have combo chains plus a Q/E skill layer and class dashes (see docs/engine_reference.md and the combo code in the working copy — read the actual combo-window/cancel implementation before proposing changes to it).
- Audio stack is ready for this: AudioManager + SoundTable autoload, weapon-fire SFX already wired via on_ability_used, and a REAPER MCP pipeline for synthesizing/rendering new SFX to assets/audio/_incoming.
- Feedback infra: CombatFeedbackManager (pooled damage numbers), hit-flash tweens, camera available for micro-shake/hitstop.
- Constraint from Ben's direction: combat must stay readable — the screen is already busy at 640x360.
</context>

<constraints>
- No beatmap, no global music-synced timing, no input windows tighter than what a keyboard+mouse player hits casually — forgiving-but-rewarding, never punishing.
- Every proposal must be implementable with existing systems (AudioManager, StatusEffectDefinition, TriggerComponent, CombatFeedbackManager) — flag anything needing new engine work.
- Estimate implementation size (S/M/L) per mechanism.
</constraints>

<reasoning_guidance>
- Separate feel-reinforcement (pitch-laddered combo-step SFX, hitstop accents on finishers, subtle visual pulse marking the cancel window) from mechanical reward (small damage/speed bonus for tight cadence). Lean feel-first; mechanical rewards risk the "overcomplicate" trap.
- Consider what the player hears/sees at combo step 1 vs step N — escalation is the rhythm-game trick that transfers cheapest.
- Consider failure feedback: what tells the player they dropped the chain, without feeling like punishment?
</reasoning_guidance>

<output_format>
Markdown design brief at docs/combo_feedback_spec.md: (1) principles borrowed and explicitly rejected, (2) mechanism menu with per-item feel goal + systems touched + S/M/L cost, (3) one recommended starter package (~3 mechanisms), (4) open questions for Ben. Max ~2 pages. No code.
</output_format>

<success_criteria>
Ben can redline it in ten minutes: every mechanism is concrete enough to approve/reject individually, grounded in the real combo implementation (cite actual file/function names), and nothing proposed requires systems the engine lacks.
</success_criteria>
